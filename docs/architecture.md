# Architecture

How Tastebook is built and run, and why. Decided in the engineering session on 2026-10-26; the rules agents follow are in [`AGENTS.md`](../AGENTS.md), and the product in the Linear team's Vision document. Items marked _planned_ are decided but not built yet; the Linear issue that builds them is named.

## Stack

| Part | Choice | Why |
| --- | --- | --- |
| Frontend | React single-page app with Vite, TanStack Query, react-router | Suits an app-like, phone-first product (cooking mode, a live shopping list); already built and working. |
| API | Django with Django REST framework, OpenAPI schema generated by drf-spectacular | Django's admin is the moderation and data-fixing tool; the generated contract keeps the two apps in step. |
| Database | Postgres | Already in use; Neon in the cloud. |
| Styling | Tailwind CSS with shadcn/ui (components copied into the repo, built on Radix) | Tastebook owns every component, Radix brings accessibility, and agents know it well. The look is decided in the design system session. _planned_ |

## Where it runs

Everything on Vercel, in one project with two [services](https://vercel.com/docs/services) (`vercel.json`): `frontend` and `backend` build separately and deploy together, so a preview's two halves always match. `/api/*` reaches Django; everything else gets the frontend. Functions run in London (`lhr1`), next to the database.

| Part | How | Why |
| --- | --- | --- |
| Frontend | Static files | Nothing to run; fast from the edge. |
| API | Django as a Python function under `/api`, on the same domain as the frontend | One platform, same-origin cookies for sign-in, no CORS. Cold starts after idle time are acceptable at this scale. |
| Database | Neon Postgres, through the Neon-managed integration from the Vercel Marketplace | Free plan covers a household app; a database branch per preview. Neon-managed rather than Vercel-managed because it deletes a preview's branch once its Git branch is gone (merged branches are deleted), which keeps within the free plan's 10 branches. One of the 10 is `previews-base`, the permanent empty branch previews are made from. |
| Photos | Vercel Blob | Native, no extra account. |
| Domain | <https://tastebook.dev>, registered through Vercel; `www.tastebook.dev` and the old address, `tastebook-app.vercel.app`, redirect to it | Until October 2026 production was at `tastebook-app.vercel.app`, because `tastebook.vercel.app` was taken and Vercel's first pick was `tastebook-sooty.vercel.app`. `.dev` is HTTPS only (HSTS preload), so nothing may build an `http://` production address. |

## Environments

| Environment | Database | Deployed when |
| --- | --- | --- |
| Local | Postgres in Docker (`compose.yaml`) | `pnpm dev` |
| Preview | Its own Neon branch, made from `previews-base`, which is empty and the Neon project's default branch | Every push to a PR |
| Production | Neon's `production` branch | Every merge to `main` |

Each build runs Django's migrations against its own database (`backend/build.py`, over Neon's direct connection; requests use the pooled one), so every deployment's schema matches its code. It then loads the catalogue from `backend/recipes/catalogue.json` with `manage.py load_catalogue`, which makes the database's recipes, ingredients and equipment what the file says, so the catalogue changes through PRs like code. The admin shows recipes, ingredients and equipment read-only, with a notice saying so, because the next deploy's load would undo an edit made there; cuisines aren't in the file, so they stay editable. A file the database can't hold fails the build. The load touches only catalogue recipes (those with no household), so households' recipes, their cuisines and their courses stay as they are.

- **Preview databases:** a preview's Neon branch is made from `previews-base`, an empty branch, so no account, household or private recipe from production ever reaches a preview. The build then migrates it and loads the catalogue, so a new preview opens with the catalogue and no accounts. As a backstop, a preview's build marks a database it finds empty (a comment on its `public` schema, which production's never has), and fails before migrating if the database isn't marked, whatever it holds (`backend/build.py`): an unmarked database was copied from another branch, so the setup below is wrong, even while the copy holds no accounts. A marked one holds only what was made on that preview, its accounts included. Setting it up is a person's step, done once in Neon and not something the repo can do; it was done on 2 Nov 2026:
  1. In the Neon console, make a branch named `previews-base` from `production` with **Schema only**, so it copies no rows, and untick **Automatically delete branch after** (the console ticks it with 1 day by default, which would delete the default branch). Then empty it in its SQL Editor with `DROP SCHEMA public CASCADE; CREATE SCHEMA public;`. It has to be empty, not only rowless: with no rows in `django_migrations`, the build's `migrate` would try to make tables that already exist. Never make it, or reset it, from production's data.
  2. The integration has no setting for the branch previews are made from: it always makes them from the Neon project's default branch. So, in this order, first pin production in Neon console › Integrations › Vercel › Manage › Branches: set **Production branch** to `production` explicitly and save. Then make `previews-base` the default branch (Branches › `previews-base` › Set as default). Redeploy production in Vercel and check it still uses `production`. The other order would leave production following the default branch onto `previews-base`'s empty database.
  3. Delete any preview branch made before the change (named `preview/<git branch>` in Neon): the integration reuses a Git branch's database branch, so the next push to that PR makes a new one from `previews-base`.

  A preview whose build fails with "This preview's database wasn't empty at its first build" was copied from another branch. Check Neon's default branch first (step 2): if it isn't `previews-base`, a new copy would come from the wrong branch too. Then delete that preview's branch (`preview/<git branch>`) in Neon and redeploy.

- **Hosts:** Django trusts the hosts Vercel gives the deployment (`VERCEL_URL`, `VERCEL_BRANCH_URL`, `VERCEL_PROJECT_PRODUCTION_URL`) and nothing else under `vercel.app`, both as allowed hosts and as CSRF trusted origins (`backend/config/settings.py`). Production's domain is trusted through `VERCEL_PROJECT_PRODUCTION_URL`, which Vercel sets to the project's production domain, so it needs no code change. Vercel only sets it on deployments made after the domain is added, though: when production's domain is added or changed, redeploy production before the API answers on it, and don't redirect the old address to the new one until then (in October 2026 the API answered 400 on `tastebook.dev` until a redeploy). `DJANGO_ALLOWED_HOSTS` adds allowed hosts but not CSRF trusted origins, so a domain listed only there would refuse sign-in and every other unsafe request.
- **Secrets:** `DJANGO_SECRET_KEY` is set per environment in Vercel, one value for production and another for previews. Neon sets `DATABASE_URL` and `DATABASE_URL_UNPOOLED`. `RESEND_API_KEY` sends sign-in emails, on production only (Accounts). `GOOGLE_OAUTH_CLIENT_ID` and `GOOGLE_OAUTH_CLIENT_SECRET` are Google's sign-in client, on production only (Accounts). Sentry sets `SENTRY_DSN`, plus `SENTRY_AUTH_TOKEN`, `SENTRY_ORG` and `SENTRY_PROJECT` for uploading source maps; none are set locally or in CI, so Sentry stays off there. The frontend's build passes the DSN, environment and commit to the browser by name (`frontend/vite.config.ts`), because Vite only exposes `VITE_*` variables.
- **Previews** are behind Vercel's sign-in (Deployment Protection). The checks on previews (TAS-26) get a bypass secret for automation. The Vercel toolbar, Comments included, is off for previews (project Settings › General › Vercel Toolbar), because Lighthouse would score its injected scripts, and in October 2026 its feedback script started setting a third-party cookie that failed Best Practices.
- **GitHub Actions secrets:** the checks on previews run from the deployed commit's own workflow file, a fork's PR included, so any repository secret is open to whoever opens a PR. The only one there is `VERCEL_AUTOMATION_BYPASS_SECRET`, which gets past previews' sign-in and nothing else. The factory's secrets (`CLAUDE_CODE_OAUTH_TOKEN`, `FACTORY_APP_CLIENT_ID`, `FACTORY_APP_PRIVATE_KEY`) are in the `factory` environment, whose deployments are limited to `main`; the factory's stage runs come from `repository_dispatch`, which runs on `main`.
- **The admin** is at `/admin/`, which `vercel.json` rewrites to Django beside `/api` (the dev server proxies it too, so local runs use one origin). It's for staff who have signed in with two factors (Accounts); its styles are under `/api/static/`.

## Accounts

- **Sign-in:** `django-allauth`'s headless API under `/api/_allauth/` (the browser client: session cookies and CSRF), with a 6-digit code sent by email that works once, for 10 minutes; no passwords. Asking for a code for an address with no account answers `unknown_email`, and the client then signs up with it, which emails a code too. Or with Google, through allauth's social login (`allauth.socialaccount`): the sign-in page posts a form to `/api/_allauth/browser/v1/auth/provider/redirect`, Google sends the browser back to `/api/accounts/google/login/callback/` (the Google client's only redirect, so allauth's own URLs are mounted at `/api/accounts/`, where under `HEADLESS_ONLY` they are only the providers' callbacks), and allauth returns it to `/sign-in?next=…`, with `?error=` when it went wrong. Signing up is the same flow. Only an address Google has verified is accepted, and it signs in to the account that already has it; a new account takes its name from the profile's first name, so it skips the name page. Google is offered only where `GOOGLE_OAUTH_CLIENT_ID` and `GOOGLE_OAUTH_CLIENT_SECRET` are set (Production secrets); without them the sign-in page shows no Google button. Google's sign-in app stays in Testing, so only its listed test users can use it, until a person adds the privacy page's address (`/privacy`, TAS-135) under Branding in the Google Cloud project and publishes the app. Nobody forgets a password they never set, Google covers most people, and accounts stay in Tastebook's own database (households and private recipes depend on them) rather than with a third party. The account is `households.User`, with the email address as its identifier. Sign-in's limits (codes per address, tries per code) are counted in Django's database cache, the `django_cache` table a migration makes, so every instance shares them; on Vercel the client's address comes from `X-Real-IP`. Django deletes expired cache rows only once the table passes `MAX_ENTRIES`, so the nightly backup workflow clears them first (`manage.py clear_expired_sign_in_limits`).
- **Sessions:** Django's database sessions, in cookies on the same domain as the API. A session lasts 30 days from its last request: every request sets the cookie again.
- **Email:** Resend over SMTP from `noreply@tastebook.dev` (`DJANGO_DEFAULT_FROM_EMAIL`), production only; `RESEND_API_KEY` is a Production secret and production won't start without it. Previews send no email; locally and in CI it goes to the console.
- **Previews:** email codes only; Google can't redirect to preview addresses that change per PR, so previews have no Google client. Since previews send no email, only test accounts sign in there: addresses at `tastebook.test` (reserved by RFC 2606, so nobody can own one), whose codes the backend stores instead of sending. End-to-end tests read them from `GET /api/test-accounts/code/?email=`, which on previews needs the previews' bypass secret in `X-Test-Account-Secret`. `POST /api/test-accounts/seed/` makes signed-in test accounts, with their households and the recipes they wrote, for end-to-end tests and verify, behind the same rules. Locally and in CI it needs nothing; on production it answers 404 and signing up refuses a `tastebook.test` address.
- **Staff:** the Django admin is for staff accounts only, and staff need two-factor sign-in with an authenticator app (`allauth.mfa`), because the admin can change every recipe and account. Staff sign in to the admin through the app's sign-in page (Django's password form is gone): signed out, `/admin/` sends you to `/sign-in?next=/admin/`; an account that isn't staff gets 404 from every admin address. The first time a staff account opens `/admin/`, it sets up its authenticator at `/admin/two-factor/` (a QR code and its key, then ten recovery codes shown once), and from then on every sign-in to Tastebook, by email code or Google, asks for the app's 6-digit code or a recovery code. The admin opens only to a session whose sign-in included that code and whose account still has the authenticator or recovery codes it came from (`households.services.may_open_admin`); a staff session that hasn't given it gets the same code page in the admin.
- **Staff accounts:** made and reset with two commands, run from `backend/` against production: `DJANGO_DEBUG=true DATABASE_URL='<production's DATABASE_URL_UNPOOLED>' uv run python manage.py make_staff you@example.com` makes an existing account staff and superuser (sign up in the app with the address first), and `reset_two_factor you@example.com`, run the same way, removes a lost phone's authenticator and recovery codes, so the next visit to `/admin/` sets up a new one.
- **Personal data, where and for how long** (UK GDPR's storage limitation; add a row with any feature that stores more or sends it to another service, and say the same on the privacy page, `frontend/src/app/privacy-page.tsx`):
  - Accounts (`households.User`): the email address and name, for as long as the account exists.
  - Google sign-ins (`socialaccount_socialaccount`): the Google account's id, its email address, whether Google verified it and its first name, for as long as the account exists. The rest of the profile (photo, full name) and Google's tokens aren't stored.
  - Sessions (`django_session`): which account a browser is signed in as, 30 days from its last request; nothing deletes expired sessions yet.
  - Authenticators (`mfa_authenticator`): a staff account's authenticator key and recovery codes, until it's reset or the account is deleted. They're stored unencrypted: anyone who can read the database can already change it.
  - Sign-in limits (`django_cache`): the client's IP address, a SHA-256 hash of the email address or the account's id, while a limit counts them (at most 10 minutes), then until the next night's clear.
  - Backups: a copy of the database, so of the rows above, kept 30 days (Backups).
  - Sentry: error reports, sent without request bodies, cookies, IP addresses or local variables (`backend/config/sentry.py`).
- **Deleting an account** (UK GDPR's right to erasure): the account's private recipes are deleted; its public recipes stay, credited to "a former member", so saved links keep working. _planned_

## Photos

- A photo is an image on Wikimedia Commons or one a household uploads. A Commons photo's recipe stores its address and credit, and pages load Commons' thumbnails straight from `upload.wikimedia.org`.
- An upload is resized in the browser before it's sent (longest side 1,600 px), then Tastebook (`POST /api/photos/`) turns it upright, drops its metadata (a phone's photo can carry where it was taken), and stores it as WebP at 330, 500, 960, 1,280 and 1,600 px in the Vercel Blob store `tastebook-photos` (`backend/recipes/photo_store.py`). The browser can't resize a HEIC in most browsers, so that one is sent as it is.
- Every photo has an unguessable address. A private recipe's photo is only reachable by someone who has its address; there's no access check per image, which would need a server in front of every request.
- Production and every preview share the store, so each environment stores under `recipes/<VERCEL_ENV>/` (`development` locally), and a recipe takes only an address in this store. A photo replaced, removed or deleted with its recipe is deleted from the store, but only by the environment that stored it: a preview's database starts as a copy, so it never deletes production's photos. A photo chosen but never saved stays in the store.
- Without `BLOB_READ_WRITE_TOKEN` (CI and local runs), uploads answer 503.

## On the phone

- Dark only (`docs/design.md`, Colour): one theme, no toggle.
- Installable to the home screen. Recipes you've opened and the week's planned recipes are kept for reading offline, cooking mode included. Nothing can be edited offline: syncing offline changes is a project of its own.
- The shopping list polls every few seconds while it's open (TanStack Query's refetch interval), not WebSockets: simple and reliable on serverless, and a second's delay doesn't matter in a shop.

## Running it

| Need | How | Why |
| --- | --- | --- |
| Errors | Sentry for the frontend and Django, free plan, through the Marketplace. Each error is tagged with its environment (`VERCEL_ENV`) and commit (`VERCEL_GIT_COMMIT_SHA`); no request bodies, cookies, user details or local variables are sent. The frontend's source maps are uploaded at build time and not deployed. Only production's browser reports errors, since a preview's sign-in redirects the tunnel's request; previews' server errors still reach Sentry. The browser sends its errors to `/monitoring` on Tastebook's own address (Sentry's `tunnel` option), and a rewrite in `vercel.json` forwards them to this Sentry project's ingest URL, fixed there so the path can't reach any other project; a new DSN means updating that rewrite. | Problems are found without someone reporting them. Ad and tracker blockers drop requests to `sentry.io`, but not to the site's own address. |
| Success measures | Events in Tastebook's own database (a plan used, cooking mode opened, an import saved without fixes), shown on a staff page. _planned._ | Measures exactly what the Vision asks, sends nobody's data elsewhere, costs nothing. |
| Backups | A nightly GitHub Action dumps production into a private Blob store, kept 30 days; see [Backups](#backups). | Neon's free plan only restores a few hours back, and losing the household's recipes is the worst thing that could happen. |
| Checks on previews | Playwright end to end, axe for WCAG 2.2 AA, Lighthouse on mobile, run by `.github/workflows/preview-checks.yml` when Vercel reports a preview deployed; results are a comment on the PR. | Work is checked as it ships, before review. Thresholds are in `AGENTS.md`, Standards. |
| Dependencies | Dependabot weekly with a 7-day cooldown; pnpm and uv ignore releases under a day old. | Routine updates without supply-chain surprises. |

## Backups

`.github/workflows/backup.yml` runs at 02:17 UTC every night (and on demand from the Actions tab). It first clears expired sign-in limits (Accounts), so no dump keeps their IP addresses; the backup runs even if that fails. It then dumps production with `pg_dump` 18 over Neon's direct connection, checks the dump holds table data, uploads it to the private Blob store `tastebook-backups` as `tastebook-<time taken>.dump`, then deletes dumps older than 30 days. The code is in `tools/backup/`.

- **Secrets:** the workflow reads `PRODUCTION_DATABASE_URL` (direct, unpooled; the clearing job reads it as `DATABASE_URL`) and `BACKUP_BLOB_READ_WRITE_TOKEN` from the GitHub environment `backups`, not the repository's secrets. Only `main` can deploy to that environment, so a workflow on any other branch can't read them. The store isn't connected to the Vercel project, so the app's own token can't read or delete backups; photos are in a different store.
- **A failed night:** the run fails and shows red in Actions, GitHub emails whoever last changed the workflow's schedule, and nothing is deleted, because pruning only follows a successful upload.
- **Keeping it running:** GitHub turns scheduled workflows off after 60 days without activity in the repo. If that happens, turn it back on from the workflow's page in Actions.

To restore, with the Postgres 18 client tools (`pg_restore`) on your `PATH`, from the repo root after `pnpm install`:

```sh
BACKUP_BLOB_READ_WRITE_TOKEN=<token> TARGET_DATABASE_URL=<direct connection string> pnpm --filter @tastebook/backup restore [tastebook-2026-10-26T021705Z.dump]
```

Leave out the dump's name to restore the latest. It drops and recreates the dump's tables in the target in one transaction, so a failed restore changes nothing.

- **Client tools on a Mac:** `brew install libpq` gives Postgres 18's `pg_restore`; it isn't linked, so put `/opt/homebrew/opt/libpq/bin` first on the `PATH` for the command.
- **The token:** Vercel → Storage → `tastebook-backups` → `.env.local`; paste the value alone, without its name or quotes.
- **The target:** a Neon branch's direct connection string (Neon console → Connect, with connection pooling off): it starts `postgresql://` and its host has no `-pooler`. Check the host is the branch you mean before running, never production's unless production is what you're recovering. Reading both values with `read -s` keeps them out of your shell history.
- **Trying it:** a restore into a copy of production looks the same whether it worked or not, so make a throwaway branch from production, change some rows on it, restore, compare it with production, then delete the branch. Tried this way on 26 Oct with the first backup: the changed rows, tables, constraints, indexes and sequences all matched production.

## Code

- Organised by domain area, the same on both sides; see `AGENTS.md`, Domain areas, and [`GLOSSARY.md`](../GLOSSARY.md). A domain-driven layout keeps each area's language and rules together, and one issue mostly touches one area.
- Abstract on the third use, not before.
- Black-box tests only: the API, rendered pages, an area's public functions, Playwright on previews. Tests that survive refactoring are the ones worth having.
- Review is adversarial, against published standards (WCAG 2.2 AA, OWASP ASVS 5.0 Level 1 and the Top 10, Core Web Vitals, UK GDPR), and each fix proposes a guard against its whole class of problem.

## No AI inside the app

Tastebook makes no paid AI calls and can't run on a personal Claude subscription. Imports use the recipe data sites publish, rules for pasted text, or a person's own Claude with the Tastebook format. The factory that builds Tastebook does use Claude, on its owner's subscription.
