# DRF keys a nested list's errors by index, and looks up each related row on its own

- **Added:** 2026-11-03 · **Applies to:** spec | implement | review · **Issue:** TAS-116
- **Paths:** `backend/**/serializers.py`, `frontend/src/**/*-api.ts`
- **Rule:** With DRF 3.18, a `many=True` nested serializer that refuses some items answers an object keyed by the index of each item that failed, as a string (`{"ingredient_lines": {"1": {"amount": ["…"]}}}`), not a list with `{}` for the items that passed; a too-long list answers `{"ingredient_lines": {"non_field_errors": ["Ensure this field has no more than 100 elements."]}}`. Write a spec's 400 bodies and the frontend's error reading to that shape. A `SlugRelatedField` inside such a list runs one query per item, so a list of up to 100 needs a field that looks every slug up at once (`IngredientSlugField` in `backend/recipes/serializers.py`). `partial=True` on the root reaches every nested serializer: on a PATCH, a line missing a required field is skipped, not refused, so its `validate` meets a `KeyError` or the model's default is saved. Validate nested input on its own serializer without `partial` (`RecipeIngredientsSerializer` in `RecipeDetailView.patch`).
- **Why:** The TAS-116 spec sketched per-line errors as `[{}, {amount: [...]}]` and expected saving 30 lines to take as many queries as 2; the tests showed the object shape and 30 extra queries, one per line's ingredient. Review of PR #125 found a PATCH with a line missing `amount_max` answered 500.
