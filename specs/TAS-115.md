# Edit the household's recipes

Linear: TAS-115

## Summary

Today a household recipe can be added (TAS-114) but never changed. This lets any member of a household edit any of its private recipes, whoever wrote it, through the same form that adds one: an "Edit recipe" button on the recipe's page opens the form filled in with the recipe, and saving goes back to the recipe with the changes. Nobody outside the household can edit it, and catalogue recipes can't be edited at all. It comes now because ingredient lines (TAS-116), the method and equipment (TAS-117) and the photo (TAS-118) are added to this form and need a way to change a recipe that already exists.

Evidence: feature. A button on a private recipe's page and a page that edits it.
Design: skip. The edit page is the approved add form (`docs/design/picnic/recipe-new*.dc.html`) filled in, and the way in is one secondary Button with an icon, as "Add a recipe" already is; `docs/design.md`'s Button rule ("Secondary: a 2 px field outline", one peach button per screen) decides it. No Dino component is new or changed.

## Product behaviour

One claim per acceptance criterion, in the issue's order:

1. Any member of a household can edit any of its private recipes, whoever wrote it.
2. Someone signed out, in another household or with no household can't edit them.
3. The outsiders test probes editing a household's private recipe.

What else holds, each proved by a test below:

- A private recipe's page has an "Edit recipe" button under its intro; a catalogue recipe's page has none.
- The edit form opens filled in with every detail the add form takes.
- Changing the title keeps the recipe's address (`/recipes/grandmas-curry-k7m2qx`).
- A catalogue recipe can't be edited: the API answers 404, and its edit address goes to the recipe.
- When two members save the same recipe, the last save wins.
- The edit form refuses what the add form refuses, with the same messages.

## Technical design

### How it works today

- `RecipeDetailView` (`backend/recipes/views.py:96`) is a `RetrieveAPIView` over `Recipe.objects.visible_to(user)`. Its class-level `extend_schema` documents the GET.
- `RecipeListView.post` (`views.py:49`) refuses a signed-out account or one with no household with 403, validates `NewRecipeSerializer`, calls `add_recipe`, maps a Django `ValidationError` to a DRF one (`__all__` → `non_field_errors`) and answers 201 with `RecipeSerializer`.
- `Recipe.save()` (`models.py:356`) sets the slug only when there is none, so a title change already keeps the address.
- `NewRecipePage` (`frontend/src/recipes/new-recipe-page.tsx`) holds the whole form: the `Draft` type, its checks, `toNewRecipe`, `ChipGroup`, `NumberInput`, `Section` and `NewRecipeForm`. `useAddRecipe` (`new-recipe-api.ts`) answers `added`, `refused` or `signed-out`.
- `RecipeIntro` (`recipe-intro.tsx:92`) ends with `RecipeGaps`, the warning Banner naming what a private recipe is missing.

### The flow

```mermaid
sequenceDiagram
  participant Page as /recipes/:slug
  participant Edit as /recipes/:slug/edit
  participant API as PATCH /api/recipes/{slug}/
  participant Service as recipes.services.edit_recipe
  Page->>Edit: "Edit recipe" (private recipes only)
  Edit->>Edit: session? else sign-in; useRecipe(slug): null → "Recipe not found", public → back to the recipe
  Edit->>Edit: RecipeForm filled from the recipe
  Edit->>API: every field the form has, with the CSRF header
  API->>API: signed in with a household? else 403
  API->>API: Recipe.objects.editable_by(user).get(slug)? else 404
  API->>API: RecipeChangesSerializer(partial=True); else 400
  API->>Service: edit_recipe(recipe, details, cuisines, courses)
  Service-->>API: ValidationError (a pair half given)? 400
  API-->>Edit: 200 Recipe
  Edit->>Page: navigate to /recipes/<same slug>, replace
```

### Backend

#### Queryset (`backend/recipes/models.py`, edit)

`RecipeQuerySet` gains, after `visible_to`:

```py
def editable_by(self, member: User) -> RecipeQuerySet:
    """The recipes a member may edit: every recipe of their household, whoever wrote it."""
    # filter(household_id=None) would match the catalogue's recipes.
    if member.household_id is None:
        return self.none()
    return self.filter(household_id=member.household_id)
```

No model field changes, so no migration.

#### Service (`backend/recipes/services.py`, edit, after `add_recipe`)

```py
def edit_recipe(
    recipe: Recipe, details: Record, cuisines: list[Cuisine] | None, courses: list[Course] | None
) -> Recipe:
    """Changes the details given and keeps the recipe's address. None leaves the cuisines or courses as they are.
    Raises ValidationError when a pair is half given, as add_recipe does."""
```

In `transaction.atomic()`: `setattr` each of `details` on `recipe`, `full_clean()`, `save()`, then `cuisines.set(...)` and `courses.set(...)` for each one that isn't `None`. It never touches `slug`, `household` or `created_by`. The caller has checked the recipe is `editable_by` the account.

#### Serializer (`backend/recipes/serializers.py`, edit, after `NewRecipeSerializer`)

```py
class RecipeChangesSerializer(NewRecipeSerializer):
    """What the form sends to edit a recipe: the fields it has, each optional. The title can't be blanked."""
```

No fields of its own: it exists so the PATCH body is `PatchedRecipeChanges` in the schema rather than `PatchedNewRecipe`. Validated with `partial=True`, DRF skips `default=list` on `cuisines` and `courses` (`Field.get_default` raises `SkipField` on a partial root), so leaving them out keeps them, and `[]` clears them. A blank or spaces-only title still answers `BLANK_TITLE`.

#### View (`backend/recipes/views.py`, edit)

- `RecipeDetailView`'s class-level `extend_schema` moves onto a `get(self, request: Request, slug: str) -> Response` that returns `super().get(request, slug=slug)`, so the PATCH gets its own, as TAS-114 did for the list.
- New method:

```py
@extend_schema(
    operation_id='recipes_partial_update',
    request=RecipeChangesSerializer,
    responses={
        200: RecipeSerializer,
        400: OpenApiResponse(description='A field, or a pair of them, is not one a recipe can hold.'),
        403: OpenApiResponse(description='Signed out, or the account has no household yet.'),
        404: OpenApiResponse(description="No recipe has this slug in the account's household: there's none, "
                                         "it's another household's, or it's a catalogue recipe."),
    },
    description="Edits a recipe of the signed-in account's household; any member may, whoever wrote it. "
    'Only the fields sent change, and the address stays as it is.',
)
def patch(self, request: Request, slug: str) -> Response:
```

It raises `PermissionDenied` unless `request.user.is_authenticated` and `request.user.household_id` is set (before any lookup, so a signed-out 403 says nothing about the slug); gets the recipe with `get_object_or_404(Recipe.objects.editable_by(request.user), slug=slug)`; validates `RecipeChangesSerializer(data=request.data, partial=True)`; pops `cuisines` and `courses` with a `None` default; calls `edit_recipe`; maps a Django `ValidationError` exactly as `post` does (copy the four lines; this is its second use); answers 200 with `RecipeSerializer` of `Recipe.objects.prefetch_related('cuisines', 'courses', 'equipment').with_ingredients_and_method().get(pk=recipe.pk)`.

`PUT` stays unanswered (405): the form sends every field it has, but not the ingredients, method or photo, so a full replace would be a lie.

#### API contract

```diff
 GET /api/recipes/{slug}/             recipes_retrieve, unchanged
+PATCH /api/recipes/{slug}/           recipes_partial_update
+  request PatchedRecipeChanges { title?, description?, cuisines?: slug[], courses?: slug[], difficulty?,
+                                 prep_minutes?, cook_minutes?, extra_minutes?, extra_label?, servings?,
+                                 yield_amount?, yield_unit?, one_pot?, source?, source_url? }
+  200 Recipe | 400 { <field>: [message], non_field_errors: [message] } | 403 | 404
```

Every field is optional in the type (lesson `patch-requests-are-partial-in-the-schema.md`); the frontend sends all of them. Regenerate `backend/schema.yml` and `frontend/src/api/schema.d.ts` and commit them with the change.

#### Outsiders test (`backend/tests/test_household_privacy.py`, edit)

`ENDPOINTS['api/recipes/<slug:slug>/']` becomes `(get('/api/recipes/no-such-recipe/'), get('/api/recipes/{recipe}/'), patch('/api/recipes/{recipe}/', {'title': 'Taken'}))`. `what_they_hold` already compares the household's recipes' slugs and titles, so an outsider's edit that landed fails it.

`useEditRecipe`'s `mutationFn: async (changes: RecipeChanges): Promise<RecipeSaving>` sends `api.PATCH('/api/recipes/{slug}/', { params: { path: { slug } }, body: changes })`:

- 200: returns `saved`. `onSuccess` sets `['recipes', slug]` to the recipe and invalidates the other `['recipes']` queries, as `useAddRecipe` does.
- 400: `refused` with `firstMessages`, which both hooks now share in this file.

## Decisions

- Changing the title keeps the address, because links, bookmarks and other members' open pages keep working; `Recipe.save()` and the glossary's Slug already say the slug is set once. Asked: does a private recipe's address change with its title? → Keep the address.
- The way in is a secondary "Edit recipe" button at the end of the recipe's intro, under the "What's missing" Banner when there is one, on private recipes only. The TAS-114 board's note says the Banner would get "Edit recipe" as its action; the button replaces that, so it shows whether or not anything is missing. Asked: where does the way into editing sit? → Button under the intro.
- When two members save the same recipe, the last save wins, field by field for every field the form sends; there's no version or 409. A household is a few people, and the alternative needs a version column, a 409 and a message. Asked: what happens to the first of two saves? → Last save wins.
- The add and edit pages render one `RecipeForm`, because it is the same form on the boards, and TAS-116 to TAS-118 add ingredient lines, steps and the photo to it once rather than twice. The rule of three is about abstracting code that looks alike; this is one form on two pages. (agent)
- `new-recipe-api.ts` becomes `recipe-form-api.ts` and holds both hooks, so `firstMessages` and the result type stay private to one file rather than being copied or extracted. `RecipeAdding` becomes `RecipeSaving` and `added` becomes `saved`, since it now answers both. (agent)
- The edit is a PATCH whose fields are each optional, not a PUT, because the form doesn't hold the ingredients, method or photo, and TAS-116 to TAS-118 will send theirs separately or add them; a field left out is kept. (agent)
- A catalogue recipe answers 404 to a PATCH, the same as another household's, because it isn't the household's to edit and editing public recipes is TAS-119's. Its edit address in the browser goes to the recipe's page, since nothing links there. (agent; the triage brief's suggestion, not asked)
- Signed out, or with no household, a PATCH answers 403 before any lookup, as adding does, so the answer says nothing about the slug. (agent)
- `editable_by` returns no recipes for an account with no household, because `filter(household_id=None)` would match every catalogue recipe. (agent)
- A 404 on Save shows "Recipe not found" in place of the form, because the recipe is gone or the member has left its household, and a retry can't succeed. (agent)
